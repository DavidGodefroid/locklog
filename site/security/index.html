Security model

What locklog protects, how, what it relies on, and what it does not do.

Pre-release, in development. No release of locklog is published yet. It is built on lockkit, and its design is public in docs/security-model.md.

What locklog protects

  • 🕶️

    Clear values

    Nothing unmasked leaves the console, except an unmask a human approves at the console (the exact spans, once). Secrets are never unmasked or pseudonymised.

  • 🧪

    Clear-text oracles

    The agent cannot learn whether a clear value it chooses occurs in the logs, except through the documented residuals.

  • 🗄️

    The log backends

    locklog reads, never writes. Backend credentials stay in the console.

  • 📜

    The record of what happened

    Every call is audited in a hash chain, without clear values.

The console is the only component that reads logs, holds credentials, keeps the pseudonym keys and decides what leaves.

Preconditions (not enforced by locklog)

Like every Lock, locklog protects the logs only from an agent that cannot reach them by another path.

  • P1 · The agent is placed apart

    The agent cannot read the logs, the Docker socket, the backends’ unauthenticated ports or the cloud metadata service directly; cannot become the console’s account; and cannot write the human’s launcher state: $XDG_RUNTIME_DIR/locklog, or ~/.local/state/locklog where there is no runtime directory, and the environment the human starts the launcher with.

  • P2 · One uid, one trust domain

    Agents of one uid are one trust domain. In the own-container recipe, the agent user must not have sudo. Otherwise every agent that mounts one locklog-run is one domain.

  • P3 · Credentials stay with the console

    Backend read credentials are held only by the console. Log shippers use write-only tokens.

A standalone .locklog/ outside lea is reviewed by the console. Placing the agent is lea’s job, or the job of your own agent container. Whether agents may join LOCKLOG_NETWORK also falls under P1: they must not.

locklog doctor

Run where the agent runs, it checks the usual ways P1 fails and never prints a response body. It looks at:

  • whether the Docker socket or DOCKER_HOST is reachable;
  • membership of the groups docker, adm and systemd-journal;
  • sudo -n and euid 0;
  • whether /var/log/journal and /var/lib/docker are readable;
  • cloud credential files in the agent’s account;
  • unauthenticated reads of the configured backends;
  • the cloud metadata credential paths.

Each finding prints a remedy. On a production profile its findings are errors and it exits 1. It also lists residuals: whether Landlock confines the console, containers with IpcMode shareable, and swarm mode.

The host-agent trial

locklog setup --agent host runs the MCP server as the image’s agent account, launched from your own account. Your agent there can still read whatever your account can, so the trial is for non-production data. The launcher’s mcp refuses production profiles.

What is not masked

locklog masks the values it detects. It does not detect:

  • person names, unless the opt-in person_name detector is on (and names outside its heuristics when it is);
  • usernames and logins in free text;
  • postal addresses;
  • private and loopback IPs (infrastructure, never detected);
  • user agents and other quasi-identifiers;
  • business ids (order and customer ids, kept so trace works);
  • base64 or hex-encoded content;
  • secrets without a known shape (short or low-entropy tokens, passwords in prose, session ids in URL paths, connection strings without userinfo).

Residuals by design

  • pseudonyms link a person’s records within an epoch (7 days by default);
  • lookup (a clear value → its pseudonym, rate-limited and audited, or approval-gated with lookup = "approved") and an approved unmask link a known value to its records. This is membership probing by equality;
  • how far a call got before its deadline reflects the content’s detector density, rounded to plan granules. Aggregate byte volume and record length are visible at granule level;
  • with the opt-in prefilter = true (refused on production), latency reveals how many records contain a clear substring.

Pseudonymised data is personal data (GDPR recital 26). The model provider receives pseudonyms, timestamps, the fields locklog does not mask and the residuals above. Tighten with redact-unknown (the production default for structured logs), your own rules, and lookup = "approved".

Containers’ logs and later mounts

Docker forces rslave propagation for a bind source inside its data root. A mount created after the console started (the /dev/shm of an --ipc=shareable container, swarm secrets) therefore appears inside the console’s read-only bind, and it appears read-write.

The console opens only <id>/<id>-json.log[.N[.gz]] for mapped ids, without crossing a mount point. Where the kernel has Landlock, it denies itself writes beneath its roots. Even so, a compromised console could read such propagated files. doctor names shareable-IPC containers and swarm mode as a residual.

Prompt injection

Log content is data. Results are JSON-escaped under an “untrusted log lines” header, with control, bidi and zero-width characters replaced. Content cannot make locklog do anything beyond the agent’s call, and nothing the agent does through locklog writes or unmasks without the human.

Report a vulnerability

Please do not open a public issue. Report it privately through a GitHub security advisory, as described in SECURITY.md. Never include real credentials, real personal data or unmasked log lines: use synthetic values.
