Your AI reads the logs,
not the people in them.

Let Claude Code, Codex, Cursor or Gemini CLI investigate your production logs. The personal data and secrets locklog detects never reach the model without your approval.

locklog lets an AI agent find when and where something broke in your logs without reading them in clear. A console held by a human, in its own account and container, reads the logs. The agent asks over MCP and gets masked, bounded, typed answers: counts, patterns, traces, lines around a hit. Emails, IPs, card numbers, national ids and the other values locklog detects become pseudonyms (⟦email:7F3KQ2M9ZD4X⟧), and secrets become ⟦secret⟧, before anything leaves the console.

Why locklog?

Logs are where personal data hides in free text: an email in an error message, a client IP in an access log, a token in a header someone logged. An agent that runs journalctl, docker logs or grep, or queries Loki with its own credentials, sends all of it to the model provider.

Highlights

  • 🕶️

    Masked by construction

    Every record is masked inside the console before any predicate runs, and a predicate holding a clear email is refused (E_PII_IN_QUERY): the agent only ever works on the masked view. Equality on a pseudonym works, so “every record of this user” still does. (The opt-in prefilter, refused on production, is the documented exception.)

  • 🔎

    Investigation tools, not a query language

    locklog_count (with buckets and first_last), locklog_patterns (new templates against a baseline), locklog_trace (one request across sources), locklog_context, locklog_search, locklog_tail. Text never goes to a backend.

  • ⚖️

    Free within budgets, approved beyond

    Reads are bounded per call and per hour. A call over a budget is refused before it touches data, and locklog_scan asks you once for the whole plan.

  • 📚

    Your sources

    Files (globs, rotation, gzip, zstd), journald (a pure-Go reader), Docker container logs, and Loki in v0.1.0 (Loki once #97 lands); Elasticsearch and OpenSearch in v0.3.0.

  • 🔒

    Read-only

    Read-only mounts, a read-only root filesystem, an allowlist of backend endpoints, no Docker socket in any locklog container, no write path to any backend.

  • 👤

    Clear values stay with you

    Reads are free. Handing a clear value to the agent waits for your approval at the console and is off by default on production.

Quick start

The trial takes about five minutes. Run it on a non-production profile: your agent runs on your own account, where it could still read the logs directly.

# 1. Install the launcher (it verifies the release and the image with cosign)
curl -fsSL https://locklog.dev/install.sh | sh

# 2. Describe your logs: setup detects files, journald and containers,
#    asks whether the profile is production (answer "no" for the trial),
#    and wires the detected agents (Claude Code, Codex, Gemini CLI)
locklog setup --agent host

# 3. The console, in a terminal you keep in view (setup prints the line;
#    containers get a profile of their own, <profile>-docker)
locklog console --profile <profile>

Then, in another terminal, ask your agent: “when did the 502s start?”. It calls locklog_count, locklog_patterns and locklog_trace; the console audits every call and asks you only when the agent wants more than the free budgets or a value in clear.

Know the limits

locklog masks the values it detects. It does not detect person names unless you enable the opt-in person_name detector, usernames and logins in free text, postal addresses, private and loopback IPs, user agents and other quasi-identifiers, business ids, base64 or hex-encoded content, or secrets without a known shape.

Pseudonymised data is still personal data under the GDPR: the model provider receives pseudonyms, timestamps and the fields locklog does not mask. And locklog protects the logs only from an agent that cannot reach them by another path: on production, that is lea’s job or your own container’s.
