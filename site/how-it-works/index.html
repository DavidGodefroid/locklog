How it works

How locklog works

A console held by a human reads the logs. The agent asks over MCP and gets masked, bounded, typed answers.

The console is the only component that reads logs, holds credentials, keeps the pseudonym keys and decides what leaves.

The agent reaches it only through its Unix socket, with the MCP server locklog mcp. Nothing unmasked leaves the console except an unmask you approve.

Where each piece runs

          read-only, non-recursive binds of the approved log directories

 agent (yours: lea, your own container, or the host for the trial)
   MCP server `locklog mcp` → its project's socket, the lock's socket volume
   read-only (peer uid checked by the kernel)

The life of a call

  1. Approved sources only. The console reads the approved sources, and only those. They are reviewed at the console’s first start and on every loosening.

  2. A byte plan first. Each call gets a byte plan from the time range and the trusted selectors only (local index, Loki label stats, ES _count). Admission, cursors and stopping points depend on the plan, never on what matched.

  3. Masked first. Every record of a planned chunk is masked before anything else (the pipeline). Then the agent’s predicates run on the masked view.

  4. Bounded, untrusted output. The answer leaves through render caps as JSON under an “untrusted content” header. It carries the pseudonym epoch and a sealed cursor to continue for free.

An unmask ticket shows the record masked, with the asked spans marked » «, the agent’s reason and what a yes lets the agent link. Secrets are never unmasked.

To read a record yourself without sending anything to the agent, press Ctrl-O at the console (lox attach <name>). The records the agent’s calls return are then printed in clear on the console’s terminal, secrets kept redacted.

By default lox run’s auto mode approves no locklog ticket: scans, unmasks and approved lookups wait for you.

A profile’s auto rules change that: auto = "full-auto", or read, unmask, lookup set to auto, ask or deny. Moving one toward auto is a policy loosening you review (docs/usage.md).

The masking pipeline

Order, fixed, per record and per field:

  1. Secret detectors and secret-looking names → ⟦secret⟧. This step is final: later steps run on its output, so a rule that pseudonymises a whole field never hashes a secret.

  2. Rules: field and label names in .locklog/pii.toml, and value lists and regexes in the console-held rule directory.

  3. Personal field names → pseudonym.

  4. Value detectors: email, phone, IBAN, card, Belgian/French/Dutch/US national ids, public IP. Person names and loose phone numbers are opt-in (detectors) for their false positives. They run on a detection view: folded, NFKC, without zero-width characters, with percent, JSON \u and HTML entities decoded.

  5. Structured mode: redact-unknown (the production default) or detect. The text = "template" setting is accepted but not applied yet.

A pseudonym is ⟦kind:ID⟧: 12 Crockford base32 characters (60 bits) of an HMAC-SHA256 under a random per-epoch key.

The key rotates every 7 days by default (pseudonym_rotation). A replaced key is deleted once it has been replaced for pseudonym_max_age (30 days by default), when the console opens the profile.

There is no pseudonym-to-value store: an unmask re-reads the record by its sealed reference.

Agent rules (locklog_pii_add) only tighten: they add masking and never remove it or change its kind. They live in the console’s home volume only, never in the project’s .locklog/, each field as a keyed digest.

The allow rules of .locklog/pii.toml apply only once approved at the console (:review).

Masking benchmark

The leak harness plants canaries of every detected kind, in every format and position, and in encoded forms: percent, JSON \u, HTML entities, look-alikes, zero-width characters.

It checks every byte that leaves the console: the engine’s answers, the IPC socket’s replies, the audit file, the MCP tools’ outputs and the hub tickets’ screens. 0 leaks, checked on every pull request.

Throughput, and the budgets derived from it: docs/performance.md.

Status and roadmap

  • v0.1.0 shipped files, journald, Docker and Loki; Elasticsearch and OpenSearch as a preview.
  • v0.2.0 makes the console hub-only, started by lox run, with per-profile auto rules.
  • v0.3.0 enforces the [locklog] section of the company’s managed configuration (managed.toml).
  • v0.4.0 adds the Elasticsearch and OpenSearch incident gates and the masked export.
