How locklog works

A console held by a human reads the logs. The agent asks over MCP and gets masked, bounded, typed answers.

The console is the only component that reads logs, holds credentials, keeps the pseudonym keys and decides what leaves. The agent reaches it only through its Unix socket, with the MCP server locklog mcp, and nothing unmasked leaves the console except an unmask you approve.

Pre-release, in development. No release of locklog is published yet. It is built on lockkit, and its design is public in docs/security-model.md.

The life of a call

  1. Approved sources only. The console reads the approved sources, and only those. The sources are reviewed at the console’s first start and on every loosening.
  2. A byte plan first. For each call it builds a byte plan from the time range and the trusted selectors only (local index, Loki label stats, ES _count). Admission, cursors and stopping points depend on the plan, never on what matched.
  3. Masked first. Every record of a planned chunk is masked first: secrets (⟦secret⟧, final), then your rules, personal field names, value detectors (email, phone, IBAN, card, BE/FR/NL/US national ids, public IP; person names and loose phone numbers opt-in) and the structured or text mode. Then the agent’s predicates run on the masked view.
  4. Bounded, untrusted output. The answer leaves through render caps as JSON under an “untrusted content” header, with the pseudonym epoch and a sealed cursor to continue for free.

The masking pipeline

Order, fixed, per record and per field:

  1. Secret detectors and secret-looking names → ⟦secret⟧. This step is final: later steps run on its output, so a rule that pseudonymises a whole field never hashes a secret.
  2. Rules: field and label names in .locklog/pii.toml, and value lists and regexes in the console-held rule directory.
  3. Personal field names → pseudonym.
  4. Value detectors on a detection view (folded, NFKC, without zero-width characters, with percent, JSON \u and HTML entities decoded): email, phone, IBAN, card, Belgian/French/Dutch/US national ids, public IP; person names and loose phone numbers are opt-in (detectors) for their false positives.
  5. Structured mode (redact-unknown, the production default, or detect). The text = "template" setting is accepted but not applied yet.

A pseudonym is ⟦kind:ID⟧: 12 Crockford base32 characters (60 bits) of an HMAC-SHA256 under a random per-epoch key. The key rotates every 7 days by default (pseudonym_rotation); a replaced key is deleted once it has been replaced for pseudonym_max_age (30 days by default), when the console opens the profile. There is no pseudonym-to-value store: an unmask re-reads the record by its sealed reference.

Agent rules (locklog_pii_add) only tighten: they add masking and never remove it or change its kind. They will be stored in the console’s home volume, never in the project’s .locklog/, once the console serves them (#64); until then the tools answer that there are no rules.

Masking benchmark

The leak harness plants canaries of every detected kind, in every format and position and in encoded forms (percent, JSON \u, HTML entities, look-alikes, zero-width characters), and checks every byte that leaves the console: 0 leaks, checked on every pull request (CI job suites, with the oracle and equivalence suites).

Status and roadmap

Pre-release, in active development. v0.1.0 ships files, journald, Docker and Loki with the standalone console. v0.2.0 adds the hub (lock up, lock approve), and v0.3.0 adds Elasticsearch, OpenSearch and the masked export.
