Install · pre-release v0.2.x

Install locklog

A launcher on the host, the console in its own container, and your agent placed where it cannot read the logs itself.

Status

locklog v0.3.0 is released. Its console is started by lox run (lockhub) only.

  • lox add locklog and the locklog console in lox run need lockhub v0.10.0 or later (lockhub#84, #86, #87).
  • The tap’s locklog formula installs v0.3.0, and the lockfamily formula includes locklog.
  • Without Homebrew, install.sh installs the latest published release of the launcher (v0.3.0 at this writing), whose verbs you can run yourself.

Follow the CHANGELOG and the releases page.

Prerequisites

  • A Linux host with the logs.
  • Docker 19.03 or later.
  • cosign, to verify the release and the image.
  • Homebrew, or (for install.sh) sudo for /usr/local/bin.
  • A terminal you keep in view, where lox run stays open.

With Homebrew

Install the Lock Family with Homebrew
brew trust davidgodefroid/tap
brew install davidgodefroid/tap/lockfamily

Homebrew asks you to trust a third-party tap once. brew install davidgodefroid/tap/locklog installs this Lock alone; lox add and lox run also need davidgodefroid/tap/lox.

  1. From the project whose logs the agent investigates, lox add locklog sets up the lock (or lox init).

    cd ~/projects/shop
lox add locklog

  2. In a terminal of its own, outside the agent, keep lox run open. Approvals live there.

    lox run

Or the launcher alone

curl -fsSL https://locklog.dev/install.sh | sh

install.sh installs the latest published release, or LOCKLOG_VERSION=vX.Y.Z.

It verifies the release with cosign before it installs a root-owned /usr/local/bin/locklog. The launcher runs the image by its signed digest.

Read the script first

Download it from locklog.dev, or from the repository (raw.githubusercontent.com/DavidGodefroid/locklog/main/scripts/install.sh):

curl -fsSLO https://locklog.dev/install.sh
less install.sh && sh install.sh

locklog update moves to another release; locklog version shows the launcher’s and the image’s versions.

Trial, on a non-production profile

Start on a non-production profile: a host agent runs on your own account, where it could still read the logs directly.

lox add locklog runs locklog’s three launcher verbs from the project (docs/setup.md):

  • locklog profile add --non-interactive: a profile from the logs this host has (files, journald, containers); never a secret.
  • locklog init claude: the agent’s .mcp.json, skill and allow list (the free tools only). Also codex, cursor or gemini.
  • locklog doctor --fix --yes: what an agent here can reach.

Then, in another terminal, ask your agent: “when did the 502s start?”. It calls locklog_count, locklog_patterns and locklog_trace: free, masked, audited.

A scan, an unmask or an approved lookup becomes a ticket that lox run shows you. With the default rules it never approves one on its own.

Attach to the console (lox attach <name>) for its own questions: the policy review at its first start.

In this trial the MCP server runs as the image’s agent account, launched from your account. The launcher’s mcp refuses production profiles (E_PRODUCTION_HOST_AGENT).

For production

On production the agent must not be able to read the logs, the Docker socket or the backends itself (precondition P1). Run it:

  • In lea

    lea runs the agent in a container of its own, with the lock’s socket mounted.

  • In its own container

    docs/setup.md has a tested Dockerfile snippet for your agent image and the docker run line. The agent user must not have sudo.

Your agent CLI’s own login is yours to set up.

Then run locklog doctor where the agent runs. It checks the common ways P1 fails; on a production profile its findings are errors.
